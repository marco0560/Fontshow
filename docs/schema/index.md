# Inventory JSON Schema

This section documents the JSON schema used by Fontshow to validate
font inventory files.

## Versions

- **1.0** – Initial informal schema (implicit)
- **1.1** – Formalized schema with structured inference and warnings

## Files

The schema supports both raw and enriched inventories.

## Schema versions and validation semantics

Fontshow supports multiple inventory schema versions in order to ensure backward compatibility while allowing progressive enrichment of metadata and analysis results.

### Supported schema versions

- **Schema 1.0**
  - Minimal, legacy-compatible schema.
  - Intended for raw inventories generated by early versions of `dump-fonts`.
  - Focuses on structural correctness and basic font identity.
  - Does **not** include inference or structured diagnostics.

- **Schema 1.1**
  - Current recommended schema.
  - Adds support for:
    - structured warnings
    - normalized charset data
    - inferred scripts and languages
    - inventory-level metadata
  - Designed to be forward-compatible with future enrichment stages.

### Validation model

Fontshow uses a **two-level validation strategy**.

#### 1. Structural schema validation (strict)

Performed by:

```python
_validate_inventory_schema_strict()
```

Characteristics:

- Uses JSON Schema validation
- Ensures the inventory strictly conforms to the declared schema version
- Raises a `ValidationError` on failure
- Intended for:
  - internal validation
  - CI
  - regression tests
  - schema development

This level is **fail-fast** and should be used when correctness is mandatory.

---

#### 2. Tolerant schema validation (public API)

Performed by:

```python
validate_inventory_schema()
```

Characteristics:

- Does **not** raise exceptions on schema violations
- Returns a list of structured warnings:

```python
{
    "code": "...",
    "message": "...",
    "severity": "info" | "warning" | "error"
}
```

- Allows:
  - partial or legacy inventories
  - forward compatibility
  - gradual migration between schema versions

This is the validation mode used by:

- `parse-inventory`
- CLI commands
- user-facing tooling

---

### Error vs Warning semantics

| Severity  | Meaning                                                  |
|-----------|----------------------------------------------------------|
| `info`    | Informational notice, no action required                 |
| `warning` | Non-fatal issue, data may be incomplete                  |
| `error`   | Structural or semantic issue that may affect correctness |

A valid inventory **may contain warnings**, but must not contain **error-level diagnostics**.

---

### Backward compatibility guarantees

- Schema **1.0 inventories remain supported**
- Missing optional fields do **not** cause failures
- Enrichment fields (`coverage`, `inference`, etc.) are optional
- Validation logic is intentionally conservative to avoid breaking existing inventories
